I also stopped at this point last time, since I realized that the do-while and two different paths for cleanup is literally a try-except-finally and it made me question what I'm even doing because "I guess the oop people were right and I'm stupid" and then I went on to think about exceptions and whether they really are a good idea or not. The conclusion I came to was that it makes it easier to write code with cleanup in a readable way, since it effectively standardizes the shape of cleanup code, and it also makes it easier to report and recover from errors. However, those things aren't because exceptions are special, they are just a product of exceptions being standardized shelf ware. The shape of cleanup code can be standardized regardless of whether you use exceptions or not, reporting access violations and stuff goes through a signal handler first anyway, so the report can just be moved there instead. The only real problem is recovering from a hardware exception anywhere in the code, but that isn't really a good idea anyway. The problem with exceptions is that it makes correct code MUCH harder to write, since you have spooky action at a distance that can happen anytime, anywhere, at present or in the future. bool
ReadFile(char* path, u8* data, umm cap, umm* size)
{
	bool succeeded = false;

	FILE* file = 0;

	do
	{
		struct stat file_info;
		BREAK_IF(stat(path, &file_info) != 0);

		*size = file_info.st_size;
		BREAK_IF(*size > cap);

		file = fopen(path, "rb");
		BREAK_IF(file == 0);

		umm read_bytes = fread(data, 1, *size, file);
		BREAK_IF(read_bytes != *size);

		succeeded = true;

	} while (0);

	if (file != 0) fclose(file);

	return succeeded;
}
